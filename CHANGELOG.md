# Changelog

All notable changes to the DevSecOps Management Portal are documented in this file.

## [Unreleased]

### Added
- **Repo Auto-Discovery & Smart Wizard (Automatyczne wykrywanie stosu)**:
  - One-Click Inspect repository analysis (`POST /api/catalog/inspect-repo`, "Scan & Auto-fill" button in service form).
  - Reads Bitbucket repository structure via REST API and automatically populates service configuration:
    - `pom.xml` -> Maven build tool, compiler Java version, Kotlin detection, JaCoCo test reporting.
    - `build.gradle` / `build.gradle.kts` / `gradle/wrapper/gradle-wrapper.properties` -> Gradle build tool, exact Gradle version and JDK, Kotlin, JaCoCo.
    - `package.json` -> Enables Node.js Stage 0 pre-build, extracts Node version from `engines.node`, detects test runners (Cypress, Jest, Angular, React).
    - `changelog.xml` / `liquibase.properties` / `db/changelog` -> Liquibase build tool for SQL/PL-SQL.
    - `pubspec.yaml` -> Flutter / Dart mobile applications.
    - `requirements.txt` / `pyproject.toml` / `setup.py` / `Pipfile` -> Python is recognised, but the portal has no Python build tool, so the scan fills in no build tool and no commands.
    - `Dockerfile` / `Containerfile` / `openshift/` / `k8s/` / `helm/` -> OpenShift deployment target (`OPENSHIFT`).
    - SonarQube default configuration -> Checks for `sonar-project.properties`; if missing, automatically infers `com.bbh:<projectKey>`, discovers multi-module configurations from Maven/Gradle manifests, detects sources/tests, and auto-fills `tools.sonar.projectKey`.
- **Bitbucket Pull Request Decoration & Shift-Left Feedback**:
  - Direct pull request decoration endpoint (`POST /api/dso/bitbucket/pull-requests/decorate`):
    - AppScan SAST: adds inline line comments on exact file and line with vulnerability description and suggested remediation, skipping findings with status `Noise`.
    - SonarQube: adds inline line comments on exact file and line for quality issues, security vulnerabilities, and code smells.
    - Static analysis consolidation: combines Nexus IQ GoldenFix safe dependency updates, SAST line comments, and SonarQube findings into a single consolidated Pull Request.
    - Dynamic analysis isolation: separates DAST findings into a second dedicated Pull Request.
- **OWASP SAMM (Software Assurance Maturity Model v2.0) Scoring & Dashboard**:
  - Implemented continuous software assurance maturity evaluation across all BBH applications and business services.
  - Objective scoring engine (`SammCalculator`) evaluating 11 automated practices across 5 SAMM business functions:
    - Governance: Strategy & Metrics (telemetry, pipeline tracking), Policy & Compliance (gating, GoldenFix).
    - Design: Security Requirements (SAST configuration, test gates), Security Architecture (containerized targets).
    - Implementation: Secure Build (standardized build tools, agent isolation), Secure Deployment (automated delivery, segregation), Defect Management (Nexus IQ SCA, SonarQube).
    - Verification: Security Testing (AppScan SAST & DAST), Requirements-Driven Testing (unit tests, Cypress, code coverage >= 60%).
    - Operations: Environment Management (version catalog pinning, environment segregation), Operational Monitoring (execution reports, InfluxDB telemetry).
  - Practice scoring (0.0 to 3.0), domain scoring, overall scoring, and maturity levels: Level 0 (Initial), Level 1 (Foundational), Level 2 (Defined), Level 3 (Optimized).
  - Hexagonal backend architecture: domain model (`com.bbh.itss.dso.portal.domain.samm`), inbound use case port (`GetSammMaturityUseCase`), application service (`SammMaturityService`), and REST controller (`SammMaturityController`) exposing `/api/samm/overview`, `/api/samm/departments`, `/api/samm/departments/{id}`, and `/api/samm/pipelines/{id}`.
  - Dedicated global OWASP SAMM section in the frontend navigation (`/samm`, `samm-overview` component):
    - Executive overview card: organization average score, level badge, total applications, and maturity level distribution.
    - 5 Domain posture cards with visual meters and practice scores.
    - Business service / department summary grid with average scores and maturity tiers.
    - Application inventory table with real-time text search, department filtering, level filtering, and column sorting.
    - Detailed application scorecard modal displaying practice scores, criteria checklists, and remediation roadmaps.
    - Deep linking from Pipeline Monitoring cards ("OWASP SAMM Scorecard" button) directly opening the application's scorecard modal.
- **SQL / PL/SQL Build Tool Support via Liquibase (`buildTool: liquibase`)**:
  - Added `LIQUIBASE` to the `BuildTool` enum in the backend catalog domain (`com.bbh.itss.dso.portal.domain.catalog.BuildTool`) and frontend TypeScript models (`BuildTool` in `models.ts`).
  - Full command mapping for Liquibase across all pipeline stages:
    - Build stage (`build.liquibase.commands`, `build.liquibase.flags`, `build.liquibase.dir`, `build.liquibase.env`, `build.liquibase.label`, `build.liquibase.returnStdout`).
    - Unit tests and verification stage (`tests.unitTests.liquibase.*`, plus JUnit XML result pattern `tests.unitTests.unitTestResult` and coverage report path `coverage.reportPath` for utPLSQL / SQL test runners).
    - SonarQube static analysis (`tools.sonar.liquibase.*`) for SQL and PL/SQL code quality and security rules.
    - AppScan SAST pre-IRX step (`asoc.liquibase.*`).
  - Automatic default command suggestions in the portal UI (`updateSQL` for build, `--changelog-file=changelog.xml` for flags, `validate` for unit tests, `sonar` for SonarQube) and dynamic field labels ("Liquibase commands", "Liquibase flags").
  - Tailored validation rules: `javaPath` and `buildToolAutoSetup` are not required when `buildTool` is `LIQUIBASE`.
  - Support for both standalone (single-module) SQL / PL/SQL repositories and multi-module / polyglot repositories combining SQL / PL/SQL services with Java, Gradle, Maven, Node.js / Angular (including Stage 0 `build.node`), Python, and Kotlin services in a combined `Jenkinsfile`.
  - Complete YAML/JSON import (`ServiceConfigReader`) and export (`DsoConfigBuilder`) round-trip support for `liquibase` services.
- **Database changes of Liquibase services (`database.changelogFile`)**:
  - Section "Database changes" of every Liquibase service. A Liquibase service without a changelog file works as before, with its Liquibase commands only. With a changelog file the pipelines also check the changes offline, package them into a zip, run the utPLSQL tests in a test database, deliver the zip to Nexus and deploy it to the RD and QC databases with the Jenkins credentials of each database, in place of the deployment of the service.
  - The `database` block is rendered after `build`, with the `database.test`, `database.rd` and `database.qc` databases. A service with database changes renders no `deployTarget`, `appName`, `artifactName`, `baseArtifactName`, `deploy` or `delivery`, and its Nexus IQ GoldenFix pipeline is refused with 409 Conflict. The form checks the JDBC URLs, the credentials IDs, the context filters and the changelog parameters, and the save checks the Nexus delivery of each pipeline type.
  - Global Settings section "Liquibase database changes": the tools, the allowed databases and the Nexus repositories of the database packages (`defaults.tools.liquibase`, `defaults.tools.oracleJdbc`, `defaults.tools.utplsql`, `defaults.database`), rendered only while they are set. The default build tool of a new service cannot be Liquibase.
  - The import reads the `database` block of a Liquibase project and never takes a database password, a JDBC URL with a user or a password, or a production database.
  - "Scan & Auto-fill" keeps the build tool, the commands and the deployment settings of a service with database changes, also when it finds Gradle or Maven at the root of the repository, and fills in only an empty SonarQube project key.
  - The Directory of the SonarQube command (`tools.sonar.liquibase.dir`) of a service with database changes must be `.` or a relative path inside the repository that holds the package folder and, while the utPLSQL tests run, the folder of the test packages, as the library checks it: the form shows the problem under the field and the save refuses it.
  - Changeset `037-sql-plsql-services.sql` adds the database columns and the table `DSO_SERVICE_DATABASE_TARGET`.
  - Guide chapter 7, "SQL and PL/SQL changes with Liquibase", describes both kinds of Liquibase service, the three repository layouts, the portal steps and the Library defaults; the examples add the products `ORDERSDB` and `ORDERSGRADLE`.
- **Service Creation & Configuration Import / Copy Workflows**:
  - **Import `devsecops_config.yaml` / `config.yaml`**: Added "Import devsecops_config.yaml" in both the Self-service wizard and the Admin product editor, parsing YAML or JSON configurations (`ServiceConfigReader`), pre-filling all matching service fields, and reporting any unimported keys or missing required fields.
  - **Copy Values from Existing Service**: Added "Copy values from existing service" when adding a service in the Self-service wizard and Admin editor, plus "Duplicate service" on existing service cards.
  - **Strict Form Validation on Service Creation**: Disabled "Add service" / "Continue" buttons whenever any required field in the current service form is invalid or incomplete, displaying clickable links to each invalid field.
  - **Standalone `devsecops_config.yaml` Download & Keyless Jenkinsfile**: Product settings download now saves as `devsecops_config.yaml` (with `config.yaml` backward compatibility on import), accompanied by a "Jenkinsfile without a key" option for repositories running without portal key lookup.
- **Jenkins Node / Agent Configuration**:
  - Added Jenkins agents (`pipeline.agentNames`) field when creating a product and in pipeline settings, defaulting to the service template agents.
- **AppScan Credentials & SAST Configuration Alignment**:
  - Removed AppScan API Key ID from the product-level creation/edit form and database table (`V8__drop_product_appscan_key_id.sql` migration); AppScan credentials (`asoc.keyId` and `asoc.token`) are now consistently configured at the service level.
  - Moved `asoc.token` (AppScan secret credentials ID) from Advanced Settings to the main AppScan SAST section.
  - Added `sast.scanName` (custom AppScan SAST scan name) to AppScan SAST Advanced Settings.
- **SonarQube Configuration & Badge Authentication Alternatives**:
  - Moved SonarQube `installationName`, `authToken`, and `badgeToken` into the main SonarQube configuration flow.
  - Added `badgeCredentialsId` (`tools.sonar.badgeCredentialsId`) as an alternative to `badgeToken` (`tools.sonar.badgeToken`), allowing users to provide either a direct badge token or a Jenkins Secret text credentials ID (mutually exclusive validation).
- **Single Nexus IQ Application per Service**:
  - Restricted the service editor UI so a service configures at most one Nexus IQ application (`tools.nexusIq.application`), while preserving read/migration compatibility for legacy multi-application services (`V6__nexus_iq_single_application.sql`).
- **Deployment & Nexus Delivery Controls**:
  - Added "Disable Nexus Delivery" checkbox mapping to `deploy.vm.rd.nexusDeliveryEnabled: false` (for Virtual Machine deployments) and `deploy.openshift.rd.nexusDeliveryEnabled: false` (for OpenShift deployments).
  - When "Disable Nexus Delivery" is checked, delivery-only fields (such as Maven delivery command on VM or artifact name on OpenShift) are automatically hidden and excluded from required-field validation.
- **Multi-Report Code Coverage & Parallel Static Analysis Settings**:
  - Updated `coverage.reportPath` to accept multi-line paths and wildcards (`*`, `?`, `**`), with automatic discovery of JaCoCo XML and LCOV reports across modules when left empty.
  - Added Global Settings toggle "Run Nexus IQ and SonarQube while AppScan scans" (`staticAnalysis.parallel`) to run AppScan SAST in the background in parallel with Nexus IQ + GoldenFix and SonarQube.
- **Node.js Stage 0 Pre-Build & Shared Version Catalogs**:
  - Added optional Node.js pre-build (`build.node.*`, Stage 0) for services with a web frontend (Angular/React/npm) alongside Gradle, Maven, or Liquibase.
  - Added `goldenFix.versionCatalogs` ("Shared version catalogs") to the GoldenFix section and combined multi-service `Jenkinsfile` generation (`pipelineKeys`) for multi-module repositories.
- **Library Defaults Pre-Population & Interactive Field Tooltips**:
  - Automatically pre-populated new service forms with values from Library defaults (Global Settings) and displayed "Library default: ..." hints and `devsecops_config.yaml` key chips on every field.
  - Added help icons (`dso-help`) with descriptive tooltips across all form fields in the portal.

### Fixed
- **Liquibase Services**:
  - Changeset 037 recreates the build tool checks of `DSO_SERVICE` and `DSO_GLOBAL_SETTINGS` with `LIQUIBASE`, which they lacked, so a Liquibase service can be saved.
  - The help of the Liquibase commands says that the library runs `validate` when they are empty, and that a new service is prefilled with `updateSQL`.
  - The guide no longer says that the library reads `tests.unitTests.unitTestResult` and `coverage.reportPath` for the utPLSQL tests of a Liquibase service: utPLSQL results and coverage come with the database changes.
- **OpenShift Targets QC Region Validation**:
  - Fixed validation in the OpenShift targets section so the QC region is completely optional when left empty, and only validates required QC deployment fields when at least one QC field is populated.
