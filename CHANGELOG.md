# Changelog

All notable changes to the DevSecOps Management Portal are documented in this file.

## [Unreleased]

### Documentation
- The user guides, `TODO.md` and `docs/MANAGEMENT_OVERVIEW.md` follow the library: the pipeline report ends with the table *Manual Actions vs DevSecOps* (one line per step in the order of the pipeline, the time by hand, the time with DevSecOps, the time gained in percent and a summary in seconds, minutes and percent), which replaces *Manual actions vs DevSecOps Automated Actions* and the table of the time one after another and in parallel. The minutes of the manual steps stay `report.manualEffort` of the library defaults and are no Global Settings value.
- Review of the library branches `DSOEnhancedWithoutPortal` and `main` and of the portal of 2026-11-20: new `TODO.md`, the prioritised list of open work for the library and the portal, and `docs/MANAGEMENT_OVERVIEW.md`, the overview for senior management; both are the same file in the three sources. *Known gaps* of the README names the build tools npm, pip, Android and iOS that the service form lacks, the differences of the repository scan from the detection of the library, and the user guides that have drifted from the copies of the library.

### Added
- **Build tools npm, pip, Android and iOS**: a service that is only Angular or Node.js, only Python, an Android app or an iOS app is configured in the portal (`NPM`, `PIP`, `ANDROID`, `IOS`, rendered as `buildTool: npm`, `pip`, `android`, `ios`). For npm the Node.js build of the service is its build (`build.node`, written also without the stage 0 switch); for pip and iOS the build is one command line (`build.pip.commands`, `build.ios.commands`); the unit tests of the three are one command line (`tests.unitTests.commands`, `tests.unitTests.dir`) and their SonarScanner takes flags only (`tools.sonar.<tool>.flags`); Android writes the Gradle blocks. The form shows only the fields the library reads, needs no JDK for npm, pip and iOS, and a save with an unused part of a command is refused. *Import config* reads the names of the library (`python`, `poetry`, `pipenv`, `node`, `nodejs`, `yarn`, `pnpm`, `angular`, `react`, `vue`, `xcode`, `swift`, `cocoapods`, `mvn`, `gradlew`, `dart`). The Library defaults offer the four as the build tool of a new service. Changeset `045-npm-pip-android-ios-build-tools` widens the build tool constraints.

### Changed
- **Where a pull request comment goes**: `POST /api/dso/bitbucket/pull-requests/decorate` reads the files the pull request changes (Bitbucket Server `changes`, Bitbucket Cloud `diffstat`) and follows the rule of the library. A finding in a changed file is a comment under its line; the findings of a file the pull request does not change are one pull request comment that names the file and each line; findings without a file are one pull request comment. When the changed files cannot be read, every finding with a line is tried under its line, as before. The remediation of a finding is shown as **Recommended fix**; the library fills it with the fix recommendation it reads from the AppScan API.
- **Scan & Auto-fill follows the detection of the library**: the order is Flutter, iOS, Maven, Gradle (Android with `AndroidManifest.xml`), .NET, Liquibase changelog, Python, npm at the root, SQL and PL/SQL files. `settings.gradle(.kts)` and `gradle/wrapper/gradle-wrapper.properties` are Gradle markers and `gradlew` alone is none; a Python repository gets the build tool pip with its build command, a repository with only `package.json` or `angular.json` the build tool npm, and the test command of both is left to the default of the library.
- **One version of the user guides**: `docs/USER_GUIDE_PORTAL` and `docs/USER_GUIDE_WITHOUT_PORTAL` are merged with the copies of the library and are the same files in the portal and in both library branches; `tools/render-user-guides.sh` renders their pages from the Markdown files.
- **SQL and PL/SQL files without a changelog**: the build tool *SQL / PL/SQL files (no changelog)* (`SQL`, rendered as `buildTool: sql`, imported from `sql`, `plsql`, `pl/sql` or `pl-sql`). Such a service always has database changes: the form shows the section Database changes without the Changelog file and switches the Liquibase commands of Build and Unit tests off, because the library writes the changelog `dso-changelog.xml` and runs Liquibase itself. *Scan & Auto-fill* chooses it for a repository with only SQL and PL/SQL files, fills the Search folder and ticks the automatic build tool setup. An import of `buildTool: sql` with a changelog or Liquibase commands of its own becomes Liquibase (SQL / PL/SQL) with a note, as the library runs it. Migration 044 adds `SQL` to the build tools of a service; the Library defaults refuse it as the build tool of a new service.
- **Gradle and Maven plugins from the BBH Nexus**: the Global Settings section *Service defaults* has the block *Gradle and Maven plugins* with the checkbox *Retry a Gradle or Maven step with these repositories when a plugin is missing* (`pluginRepositories.enabled`, ticked by default), *Gradle plugin repository* (`pluginRepositories.gradle`) and *Maven plugin repository* (`pluginRepositories.maven`), each an http or https address of letters, digits and `. _ / + @ : = , ~ % -` only. The portal renders them under `defaults.pluginRepositories`; an empty repository is left out, so the library uses the one of its own defaults. *Import config* notes the three keys of a service as Global Settings values. Liquibase changeset 043 adds `PLUGIN_REPOSITORIES_ENABLED`, `GRADLE_PLUGIN_REPOSITORY` and `MAVEN_PLUGIN_REPOSITORY` to `DSO_GLOBAL_SETTINGS`, with 1 and the repositories of the BBH Nexus for the saved settings; a `PUT /api/settings` without the fields ticks the box and leaves the repositories empty.
- **Stages at the same time**: the Global Settings block *Speed* has the new checkbox *Run the regression, smoke and performance tests and DAST at the same time* (`dynamicAnalysis.parallel`, ticked by default) next to *Run unit tests, Nexus IQ, SAST and SonarQube at the same time* (`staticAnalysis.parallel`, formerly *Run Nexus IQ and SonarQube while AppScan scans*, ticked by default), and both help texts describe the parallel branches of the library. The portal renders `defaults.dynamicAnalysis.parallel`, and *Import config* notes `dynamicAnalysis.parallel` of a service as a Global Settings value. Liquibase changeset 042 adds `PARALLEL_DYNAMIC_ANALYSIS` to `DSO_GLOBAL_SETTINGS`, 1 for the saved settings; a `PUT /api/settings` without `scans.parallelDynamicAnalysis` ticks it.
- **Nexus delivery upload and download**: a Maven or Gradle service on virtual machines lists the files of its snapshot upload and of the download of the Extended pipeline under Deployment. The portal renders `delivery.push.maven` (with the goals of the upload and its `artifacts`; without artifacts `delivery.maven` and `build.buildPath` as before), `delivery.push.gradle` (`group`, `artifact`, `repositoryUrl`, `allowInsecureProtocol`, `artifacts`, flags and environment variables) and `delivery.pull` (`outputDirectory`, `group`, `artifact` and the `maven` or `gradle` block with its `artifacts`). *Import config* reads them back, keeps one group, artifact and repository for the upload and the download and notes a different second one. Liquibase changeset 041 adds the `NEXUS_DELIVERY_*` columns to `DSO_SERVICE`.

- **C# / .NET services**: the build tool `DOTNET` (rendered as `buildTool: dotnet`, imported from `dotnet` or `msbuild`) with its optional commands under `build.dotnet`, `tests.unitTests.dotnet`, `tools.sonar.dotnet` and `asoc.dotnet`; no JDK and no commands are required, since the library detects the .NET mode on the agent. The repository scan selects it from `*.sln`, `*.csproj`, `*.fsproj`, `*.vbproj`, `global.json`, `Directory.Packages.props`, `Directory.Build.props`, `packages.config` or `build.cake`. Liquibase changeset 038 allows `DOTNET` in `DSO_SERVICE` and `DSO_GLOBAL_SETTINGS`.
- **Auto-resolved settings**: *Scan & Auto-fill* returns `resolvedParameters` (setting, value, why) and the service form lists them under the result. A report upload may carry the library's `autoResolved` list (service, setting, value, why), which is stored with the run (`DSO_PIPELINE_REPORT.AUTO_RESOLVED`) and returned by `GET /api/pipelines/{id}/report`.
- **Repo Auto-Discovery & Smart Wizard (Automatyczne wykrywanie stosu)**:
  - One-Click Inspect repository analysis (`POST /api/catalog/inspect-repo`, "Scan & Auto-fill" button in service form).
  - Reads Bitbucket repository structure via REST API and automatically populates service configuration:
    - `pom.xml` -> Maven build tool, compiler Java version, Kotlin detection, JaCoCo test reporting.
    - `build.gradle` / `build.gradle.kts` / `gradle/wrapper/gradle-wrapper.properties` -> Gradle build tool, exact Gradle version and JDK, Kotlin, JaCoCo.
    - `package.json` -> Enables Node.js Stage 0 pre-build, extracts Node version from `engines.node`, detects test runners (Cypress, Jest, Angular, React).
    - `changelog.xml` / `liquibase.properties` / `db/changelog` -> Liquibase build tool for SQL/PL-SQL.
    - `pubspec.yaml` -> Flutter / Dart mobile applications.
    - `requirements.txt` / `pyproject.toml` / `setup.py` / `Pipfile` -> Python is recognised, but the portal has no Python build tool, so the scan fills in no build tool and no commands.
    - `Dockerfile` / `Containerfile` / `openshift/` / `k8s/` / `helm/` -> OpenShift deployment target (`OPENSHIFT`).
    - SonarQube default configuration -> Checks for `sonar-project.properties`; if missing, automatically infers `com.bbh:<projectKey>`, discovers multi-module configurations from Maven/Gradle manifests, detects sources/tests, and auto-fills `tools.sonar.projectKey`.
  - Pipeline runtime auto-resolution (`RepoStackAutoResolver`) enabled by default (`autoresolve parameters: true`) across both portal-integrated and standalone execution modes, allowing minimal configurations (`appId` only).
- **AppScan REST API v4**:
  - The library signs in to AppScan on Cloud through the REST API v4 with the one API key of the functional user from its defaults, for SAST and DAST of every service.
  - Automatically filters out findings with status `Noise` from AppScan SAST reports.
- **Bitbucket Pull Request Decoration & Shift-Left Feedback**:
  - Direct pull request decoration endpoint (`POST /api/dso/bitbucket/pull-requests/decorate`):
    - AppScan SAST: adds inline line comments on exact file and line with vulnerability description and suggested remediation, skipping findings with status `Noise`.
    - SonarQube: adds inline line comments on exact file and line for quality issues, security vulnerabilities, and code smells.
    - Static analysis consolidation: combines Nexus IQ GoldenFix safe dependency updates, SAST line comments, and SonarQube findings into a single consolidated Pull Request.
    - Dynamic analysis isolation: separates DAST findings into a second dedicated Pull Request.
- **OWASP SAMM (Software Assurance Maturity Model v2.0) Scoring & Dashboard**:
  - Implemented continuous software assurance maturity evaluation across all BBH applications and business services.
  - Objective scoring engine (`SammCalculator`) evaluating 11 automated practices across 5 SAMM business functions:
    - Governance: Strategy & Metrics (telemetry, pipeline tracking), Policy & Compliance (gating, GoldenFix).
    - Design: Security Requirements (SAST configuration, test gates), Security Architecture (containerized targets).
    - Implementation: Secure Build (standardized build tools, agent isolation), Secure Deployment (automated delivery, segregation), Defect Management (Nexus IQ SCA, SonarQube).
    - Verification: Security Testing (AppScan SAST & DAST), Requirements-Driven Testing (unit tests, Cypress, code coverage >= 60%).
    - Operations: Environment Management (version catalog pinning, environment segregation), Operational Monitoring (execution reports, InfluxDB telemetry).
  - Practice scoring (0.0 to 3.0), domain scoring, overall scoring, and maturity levels: Level 0 (Initial), Level 1 (Foundational), Level 2 (Defined), Level 3 (Optimized).
  - Hexagonal backend architecture: domain model (`com.bbh.itss.dso.portal.domain.samm`), inbound use case port (`GetSammMaturityUseCase`), application service (`SammMaturityService`), and REST controller (`SammMaturityController`) exposing `/api/samm/overview`, `/api/samm/departments`, `/api/samm/departments/{id}`, and `/api/samm/pipelines/{id}`.
  - Dedicated global OWASP SAMM section in the frontend navigation (`/samm`, `samm-overview` component):
    - Executive overview card: organization average score, level badge, total applications, and maturity level distribution.
    - 5 Domain posture cards with visual meters and practice scores.
    - Business service / department summary grid with average scores and maturity tiers.
    - Application inventory table with real-time text search, department filtering, level filtering, and column sorting.
    - Detailed application scorecard modal displaying practice scores, criteria checklists, and remediation roadmaps.
    - Deep linking from Pipeline Monitoring cards ("OWASP SAMM Scorecard" button) directly opening the application's scorecard modal.
- **SQL / PL/SQL Build Tool Support via Liquibase (`buildTool: liquibase`)**:
  - Added `LIQUIBASE` to the `BuildTool` enum in the backend catalog domain (`com.bbh.itss.dso.portal.domain.catalog.BuildTool`) and frontend TypeScript models (`BuildTool` in `models.ts`).
  - Full command mapping for Liquibase across all pipeline stages:
    - Build stage (`build.liquibase.commands`, `build.liquibase.flags`, `build.liquibase.dir`, `build.liquibase.env`, `build.liquibase.label`, `build.liquibase.returnStdout`).
    - Unit tests and verification stage (`tests.unitTests.liquibase.*`, plus JUnit XML result pattern `tests.unitTests.unitTestResult` and coverage report path `coverage.reportPath` for utPLSQL / SQL test runners).
    - SonarQube static analysis (`tools.sonar.liquibase.*`) for SQL and PL/SQL code quality and security rules.
    - AppScan SAST pre-IRX step (`asoc.liquibase.*`).
  - Automatic default command suggestions in the portal UI (`updateSQL` for build, `--changelog-file=changelog.xml` for flags, `validate` for unit tests, `sonar` for SonarQube) and dynamic field labels ("Liquibase commands", "Liquibase flags").
  - Tailored validation rules: `javaPath` and `buildToolAutoSetup` are not required when `buildTool` is `LIQUIBASE`.
  - Support for both standalone (single-module) SQL / PL/SQL repositories and multi-module / polyglot repositories combining SQL / PL/SQL services with Java, Gradle, Maven, Node.js / Angular (including Stage 0 `build.node`), Python, and Kotlin services in a combined `Jenkinsfile`.
  - Complete YAML/JSON import (`ServiceConfigReader`) and export (`DsoConfigBuilder`) round-trip support for `liquibase` services.
- **Database changes of Liquibase services (`database.changelogFile`)**:
  - Section "Database changes" of every Liquibase service. A Liquibase service without a changelog file works as before, with its Liquibase commands only. With a changelog file the pipelines also check the changes offline, package them into a zip, run the utPLSQL tests in a test database, deliver the zip to Nexus and deploy it to the RD and QC databases with the Jenkins credentials of each database, in place of the deployment of the service.
  - The `database` block is rendered after `build`, with the `database.test`, `database.rd` and `database.qc` databases. A service with database changes renders no `deployTarget`, `appName`, `artifactName`, `baseArtifactName`, `deploy` or `delivery`, and its Nexus IQ GoldenFix pipeline is refused with 409 Conflict. The form checks the JDBC URLs, the credentials IDs, the context filters and the changelog parameters, and the save checks the Nexus delivery of each pipeline type.
  - Global Settings section "Liquibase database changes": the tools, the allowed databases and the Nexus repositories of the database packages (`defaults.tools.liquibase`, `defaults.tools.oracleJdbc`, `defaults.tools.utplsql`, `defaults.database`), rendered only while they are set. The default build tool of a new service cannot be Liquibase.
  - The import reads the `database` block of a Liquibase project and never takes a database password, a JDBC URL with a user or a password, or a production database.
  - "Scan & Auto-fill" keeps the build tool, the commands and the deployment settings of a service with database changes, also when it finds Gradle or Maven at the root of the repository, and fills in only an empty SonarQube project key.
  - The Directory of the SonarQube command (`tools.sonar.liquibase.dir`) of a service with database changes must be `.` or a relative path inside the repository that holds the package folder and, while the utPLSQL tests run, the folder of the test packages, as the library checks it: the form shows the problem under the field and the save refuses it, with one message that names each folder the directory leaves out. For such a service the form also refuses, under the Source folder, a source folder that is not `.` or a relative path inside the repository, as the save does; while the Source folder or the Search folder is refused, the directory is not compared with the package folder and the folder of the test packages.
  - Changeset `037-sql-plsql-services.sql` adds the database columns and the table `DSO_SERVICE_DATABASE_TARGET`.
  - Guide chapter 7, "SQL and PL/SQL changes with Liquibase", describes both kinds of Liquibase service, the three repository layouts, the portal steps and the Library defaults; the examples add the products `ORDERSDB` and `ORDERSGRADLE`.

### Changed
- **Disable Nexus Delivery** is rendered as `delivery.nexusDeliveryEnabled: false` instead of `deploy.<target>.rd.nexusDeliveryEnabled: false`. The library reads the new key first and the old one without it, so existing configs keep working, and the import reads both, noting an old key that the new one overrides.
- **One AppScan API key for every service**: the AppScan API key ID and the secret credentials ID are gone from the service form, the Self-service wizard, the API (`appScan.keyId`, `appScan.secretCredentialsId`) and the rendered configuration (`asoc.keyId`, `asoc.token`). The library signs in with the API key of the functional user, which the DevSecOps team sets in `asoc.keyId` and `asoc.token` of its `resources/com/bbh/devsecops/defaults.yaml`; a service needs only its AppScan application ID. The import of a `devsecops_config.yaml` notes `asoc.keyId` and `asoc.token` as not imported. Liquibase changeset 040 drops `APPSCAN_KEY_ID` and `APPSCAN_SECRET_CREDENTIALS_ID` from `DSO_SERVICE`.
- **GoldenFix pre-check runs the unit tests**: the help texts of the GoldenFix commands name the new library defaults, which build the fix and run its unit tests (`mvn -B -q test`, `./gradlew test`, `npm test`, `pytest`, `flutter test` or `dart test`, `dotnet test`); classic .NET Framework projects on Windows are still only restored and built.
- **GoldenFix rules are fixed**: the library raises only direct dependencies, only to a patch-level version (`1.2.3` may become `1.2.5`, never `1.3.0` or `2.0.0`), and opens a pull request only after the pre-check build of the upgraded manifests passes. The settings *Only direct dependencies* and *Verify with a build* are removed from the service form, the global settings and the API; `goldenFix.onlyDirectDependencies` and `goldenFix.verify.enabled` are no longer written, and an imported configuration that still carries them is accepted and the keys are ignored. The old `DSO_SERVICE` and `DSO_GLOBAL_SETTINGS` columns stay in the database, unmapped.
- **NuGet in GoldenFix**: `nuget` joins the GoldenFix ecosystems (also in the global defaults), and the pre-check command for NuGet is written as `goldenFix.verify.commands.nuget`. Liquibase changeset 039 adds `GOLDEN_FIX_VERIFY_NUGET` to `DSO_SERVICE` and `DSO_GLOBAL_SETTINGS`.

### Fixed
- **Scan ID uniqueness**: a service without its own Bitbucket repository (it uses the pipeline repository) may share an AppScan application ID or a SonarQube project key with another service, so a copied service with an empty repository is valid.
- **Liquibase Services**:
  - Changeset 037 recreates the build tool checks of `DSO_SERVICE` and `DSO_GLOBAL_SETTINGS` with `LIQUIBASE`, which they lacked, so a Liquibase service can be saved.
  - The help of the Liquibase commands says what the library runs when they are empty: `updateSQL` with the changelog it finds, through the run-time auto-resolve, and for a service with database changes `validate` only when Flags is set. A new service is prefilled with `updateSQL`.
  - The guide no longer says that the library reads `tests.unitTests.unitTestResult` and `coverage.reportPath` for the utPLSQL tests of a Liquibase service: utPLSQL results and coverage come with the database changes.
- **GUI specs**:
  - The menu that the smoke spec expects names OWASP SAMM, and the stub API answers the HTML report of a pipeline with an empty report, as the backend does, so the pipeline pages of the monitoring and smoke specs no longer log a 404.
- **OpenShift Targets QC Region Validation**:
  - Fixed validation in the OpenShift targets section so the QC region is completely optional when left empty, and only validates required QC deployment fields when at least one QC field is populated.
